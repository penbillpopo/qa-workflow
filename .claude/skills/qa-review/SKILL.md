# qa-review：讀意見、改文件、回心得

> **回覆使用者時**：一律依照 `CLAUDE.md` 的「怎麼跟使用者說話」，用教學、引導的方式回覆。使用者可能完全不懂程式：說清楚現在在第幾步、剛剛做了什麼、他現在要做什麼（點哪裡、打什麼字）、接下來會發生什麼。不要對使用者提技能名稱或程式檔名。

遵守 `CLAUDE.md` 的「文件互動方式」。

## 1. 找到單子

- 使用者有說單號就用那張。沒說就找 `ticket.md` 狀態為「討論中」的單，只有一張就用它，有多張就問。
- 討論文件連結在 `ticket.md` 開頭。

## 2. 讀完整份文件

用 Claude Docs 工具讀，不要用網頁抓取：

1. 有上次讀到的版本號就用 `sinceRev` 只看變動；沒有就讀整個大綱。
2. 案例表格要整張讀（`view` 加表格的 `parentId`），記下每列的「測試方式」「要不要測」下拉值和「你的意見」。
3. 兩份勾選清單要整份讀，記下勾選狀態和使用者在項目後面打的字。
4. 用 `query` 列出所有留言。

## 3. 照理解修改

- 意見沒有固定格式。看得懂就直接改：改案例文字、改預期結果、新增案例列、把可補測項目移進表格。
- 新增的案例列要補齊下拉選單與空白的意見格，編號接在最後。
- 意見處理完，就把那一格的文字刪掉。
- 無法判斷意思的意見先留著，在心得裡列出可能的解讀並反問。
- 待確認問題的回答，要寫進 `ticket.md` 的對應段落，並更新受影響的案例。
- 使用者的決定和驗收條件衝突時，照使用者的決定改，在心得裡提醒風險。
- 修改後更新表格上方的統計數字，以及「現在就能測」的說明。

## 4. 回覆心得

在對話裡回覆，結構固定：

1. 統計表：要測、AI 測試、人工測試、不測，各幾條。
2. 逐條處理：每則意見一行，說明改了什麼。
3. 需要反問的：列出解讀選項。
4. 還沒處理的事：沒回答的待確認問題、阻擋開測的條件。

## 5. 定案

使用者明確說「定案」或同等意思時才做：

1. 在單號資料夾寫 `test-cases.md` 快照，只放「要測」的案例。欄位：編號、標題、測試方式、前置條件、步驟、預期結果、TestRail 編號（先留空）。
   - 每條要展開成三到六個步驟，每步都要有可截圖驗證的預期結果，供 TestRail 的分步範本使用。
   - 「不要」的案例列在最後的「本次不測」清單，附上原因。
2. `ticket.md` 狀態改為「已定案」。
3. 用白話告訴使用者下一步：把定案的案例建進 TestRail（公司記錄測試的網站），會先列出要建什麼，等他同意才動手。
